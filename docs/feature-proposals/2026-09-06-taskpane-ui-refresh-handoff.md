## 1. 現状仕様(As-Is)

### 1.1 画面構成(`public/taskpane.html`)

上から順に:

1. ヘッダー: ブランド名 + LLM 接続状態ドット
2. `prompt`(textarea, 5行): 「スライドにしたい内容」
3. `context`(`<details>` 内 textarea, 8行、既定は閉じている): 「素材テキスト(任意)」— 議事録等の貼り付け専用欄
4. `hint`(text input): 「レイアウトの希望(任意・弱い制約)」
5. `model`(select)と`preset`/`accent`/`accentHex`(強調色)が横並びの2カラム
6. `refBox`: 参照スライド解析結果の表示テキスト + 「再解析」ボタン
7. `go`ボタン(「スライド生成 Ctrl+Enter」)+ モックチェックボックス
8. `progress`(生成中のみ表示): 3ステップの `<ol>`(① LLM生成 ② スライド描画 ③ 完了)+ 経過秒数
9. `sections`(入力が多い場合のみ表示): 章構成の確認・編集UI
10. `result`(生成後のみ表示): PNGプレビュー画像一覧 + メタ情報 + 「スライド仕様JSON」editable textarea + 再描画ボタン
11. フッター: 固定の説明文言(1行)

### 1.2 起動時フロー(`taskpane.js` `Office.onReady`)

1. `setAccent("auto")` … 強調色を「自動」に
2. `loadSettings()` … localStorage から前回値を復元(prompt/context/hint/model/accent)
3. `refreshHealth()` … `/api/health` でLLM接続状況、`/api/models` でモデル一覧を取得し `select#model` に反映
4. `refreshReference()` … `SlideRender.prepare()` を呼び、選択中スライドの構造解析結果を `refInfo` に表示

→ **構造解析(`prepare()`)は Addin を開いた時点で自動的に1回走る。** 「再解析」ボタンで手動再実行できる。
この2点は今回のブレストの要望とすでに一致している。

### 1.3 生成フロー(`generate()`)

1. `go` クリック or Ctrl+Enter → `generate()` 実行
2. **`SlideRender.prepare()`(構造解析)と `/api/generate`(LLM呼び出し)を並行実行する。**
   → つまり構造解析が終わっていなくても `go` ボタンは押せる。解析に失敗/未完了なら
     `prepared` が古い値 or `null` のまま進み、`renderSpecs` 側で自動的に既定レイアウト(`layout`モード)にフォールバックする。
3. LLM応答が `sections`(章立て提案)を含む場合は `sections` UI を表示して中断、ユーザー確定後に章ごと並列生成
4. それ以外は `SlideRender.renderSpecs()` で PowerPoint に描画 → `result` セクションにPNGプレビューとJSONを表示
5. 進捗表示は `progress` 内の3ステップ `<li>` に active/done クラスを付け替え、各ステップの所要秒数をテキストで書き込む方式

### 1.4 構造解析の詳細(`render.js`)

- `prepare()`: プレゼンのサイズ、選択中スライドID、**選択中スライドが属するマスタとそのレイアウト一覧**、
  選択中スライドの全シェイプ詳細(位置・サイズ・テキスト・フォント・色・プレースホルダ種別)を1回の
  `PowerPoint.run` でまとめて取得する。
- `pickLayoutId(layouts)`: マスタが持つレイアウト一覧から「白紙/Blank」に近い名前を正規表現でヒューリスティック
  検索し、無ければ最後のレイアウトを使う。**レイアウトをユーザーに選ばせるUIは現状存在しない**(自動選択のみ)。
- `analyzeReference(shapes, W, H)`: 選択中スライドの実物を解析し、タイトル/リード文(あれば)/フッター帯/
  出典行/本文領域(x,y,w,h)/強調色/フォント名を推定する。表紙・中表紙・タイトル不明・本文領域が狭すぎる
  場合は `profile: null` を返し、`mode: "layout"`(白紙レイアウトに既定描画)にフォールバックする。
  推定に成功すれば `mode: "clone"`(選択スライドを複製し、タイトル/リード/出典だけ文字を差し替え、
  他の装飾は保持、本文だけ新規描画)になる。
- つまり **「マスタを見て置き場所を決める」のではなく「選択中スライドの実物を解析する」のが現状の主経路**。
  マスタ側は「どのマスタ/どのレイアウトに新規スライドを追加するか」を決めるためだけに参照される
  (`mode: "layout"` のフォールバック時のみ使用)。

### 1.5 サーバ側の入力の扱い(`server.js` / `server/prompt.js`)

- `/api/generate` は `{ prompt, context, hint, model, mock, maxSlides }` を受け取る。
- `buildMessages()` は `prompt` と `context` を別セクションとしてLLMに渡すだけ
  (`【素材(コンテキスト)】` セクションと `【指示】` セクションを分けて連結)。
- **`prompt` 欄に資料をそのまま貼っても、LLM側の扱いとしては特に問題は起きない**
  (`【指示】` セクションに入るだけで、区別は主にUI上の見せ方の問題)。

## 2. 今回の変更要望(To-Be)

ユーザーのブレストから抽出した変更点。番号は実装時のタスク分割の目安。

### T1. 入力欄を1つに統合(確定)
- 「素材テキスト」の `<details>`(`context`)を廃止し、`prompt` の1つのtextareaに一本化する。
- 「たたコピペで文書入れる感じ」= ユーザーは資料をそのまま `prompt` に貼り付けるだけにしたい。
- **サーバ側 `buildMessages` の変更は不要**(1.5節参照)。UI側で `context` を送らない/`prompt` に統合するだけでよい。
- `hint`(レイアウトの希望)欄は**存置。ただし明示的に Optional な入力として扱う**(2026-09-06 ユーザー回答で確定)。
  必須感を出さない(プレースホルダーで「任意」を明示、視覚的な優先度も `prompt` より低くする)。

### T2. 下部の「地味ゾーン」に、モデル・カラー・構造解析ステータスをまとめる(確定)
- 現状は上部の目立つ2カラム(モデル/強調色)と、独立したセクション(`refBox`: 参照スライド解析結果+再解析ボタン)に分かれている。
- **これらは「ユーザーに構造解析という概念を意識させたくない」設定・状態表示**という共通点があるため、
  画面下部(フッター寄り)にまとめて、控えめな文字サイズ・視認性で配置する(2026-09-06 ユーザー回答で確定)。
- 強調色UIの刷新: 現状の `select#preset` + `input[type=color]` + hex textの3点セットをやめ、
  **色スウォッチ(丸/四角のプリセット色見本)を並べるだけの表示**にする。
  - マウスオーバーでカラーコード等の補足を出す(tooltip)。
  - クリックすると、いわゆる「色の変更」モーダル(汎用カラーピッカー)を開いてカスタム色を選べる程度でよい
    (凝ったUIは不要、ブラウザ標準 `<input type="color">` をトリガーするだけでも要件は満たせる)。
  - 「自動(参照スライドに合わせる)」の扱いは維持(スウォッチの先頭に「自動」を1つ置く形を想定)。
- 構造解析ステータス(`refBox`)もこの地味ゾーンに移す。**「解析」という文言は一切出さない。
  小さいアイコン+ツールチップのみで状態を示す**(2026-09-06 確定)。
  - 状態: 解析中(スピナー/淡色アイコン)/ 完了(通常アイコン、ツールチップに「◯×◯pt・テンプレ追従」等の詳細)/
    失敗(警告色アイコン、ツールチップにエラー概要)の3状態。
  - 常時テキストラベルは出さず、ツールチップ(hover)でのみ詳細を見せる。
  - 再解析は同じアイコンをクリック(または隣接する小さな再読み込みアイコン)で実行する。

### T3. 構造解析が終わるまで生成不可にする(確定・仕様変更)
- 現状は「構造解析とLLM呼び出しを並行実行」(1.3節)。ユーザーは「構造解析が終わるまで生成自体できない」
  という制約に同意している。
- 実装方針: `refreshReference()` の完了(成功/失敗いずれか確定するまで)を待って `go` ボタンの `disabled` を
  制御する。Addin起動直後は解析中につき `go` を disabled、解析完了で enabled にする。
  「再解析」を押した場合も、解析中は再度 disabled にする。
- 副作用: `generate()` 内で `prepare()` を並行実行している現状ロジックは、
  「解析はすでに完了している」前提に変えられるため、`prepP` の並行実行は不要になり
  `prepared` をそのまま使う形に簡略化できる。
- **解析失敗時の挙動(確定)**: 解析中のみ `go` を disabled にし、**成功・失敗いずれの確定後も enabled に戻す**。
  失敗時は `mode: "layout"`(既定レイアウト)で生成すること自体は可能なため、ユーザーを生成不能な状態に
  固定しない。失敗はT2のステータスアイコン(警告色+ツールチップ)で伝える。

### T4. 進捗表示をボタン内テキストに統合(確定・UI簡略化)
- 現状の3ステップ `<ol>`(①LLM生成 ②描画 ③完了)+ 経過秒数の専用セクションを廃止。
- 理由: 「たいしたステップを踏んでいない」= LLM呼び出し→描画の2段階程度なのに、UIが仰々しい。
- 変更後イメージ: `go` ボタン自体のラベルを状態に応じて書き換える。
  - 待機中: 「スライド生成 (Ctrl+Enter)」
  - 生成中: 「生成中… 2.3s」のようにボタン内でラップして経過時間を表示(ボタンは無効化)
  - 完了後: ボタンラベルを「再生成 (Ctrl+Enter)」等に変え、ユーザーがプロンプトを書き直して
    そのまま Ctrl+Enter で再度回せる状態にする。
- 実装方針: `stage()`/`startTimer()`/`stopTimer()` の対象を `progress` セクションの `<li>` 群から
  `go` ボタンのテキストノードに置き換える。`elapsed` の `setInterval` 更新ロジックは流用できる。
- エラー表示(`#error`)は現状通り独立して残す(ボタン内に混ぜない)。

### T5. プレビュー(PNGサムネイル)を廃止(提案・要最終確認)
- 理由: 「生成物がPPT側に出てくるんだもん」= 実機のPowerPointに直接挿入されるため、
  タスクペイン内に別途プレビュー画像を表示する意味が薄い、という指摘。
- 影響範囲:
  - `taskpane.js` の `showResult()` 内、`results.forEach` で `img` 要素を作る箇所(`previews`)を削除。
  - `render.js` `renderSpecs()` 内の `getImageAsBase64` 呼び出し(`opts.preview !== false && info.has18` の分岐)は、
    **デバッグスナップショット(`DEBUG_SNAPSHOT=1` → `debug/`保存)にも使われている**ため、
    プレビュー表示用途だけを止めて、PNG取得自体は残す(呼び出し元で `preview:false` を渡さない限り
    デバッグ用途が壊れる)。→ **サムネイルをUIに出さないだけで、PNG取得ロジックは削除しない**。
- `meta` の統計テキスト(枚数・モード・サイズ・描画時間・トークン数)は有用なので残す。
- 「スライド仕様JSON(編集して再描画)」の `<details>` は**開発者向けに隠す**(2026-09-06 確定)。
  一般ユーザー向けUIからは非表示にし、既存の開発用フラグ(`DEV_TRIGGER`等)や隠しトグルと同様の
  「開発者モード」条件下でのみ表示する。機能自体(`redraw()`ロジック)は削除しない。

### T6. マスタのレイアウト選択をユーザーに委ねる(確定・今回スコープに含む・ドロップダウンのみ)
- 2026-09-06 確定: 今回の刷新スコープに含める。UIは**ドロップダウンのみ**(サムネイル画像は無し。実装コストとのバランス)。
- 配置: T2の「地味ゾーン」に、モデル・カラーと並べて小さなセレクトを追加する。
- 効く範囲: 現状 `pickLayoutId()` は名前ヒューリスティックによる自動選択のみで、
  「マスタの中のどのレイアウトを使うか」をユーザーが指定する手段がない。
  **主経路は「選択中スライドの実物解析(clone)」であり、このレイアウト選択が効くのは
  `mode: "layout"`(参照スライドが使えない = 表紙/空スライド等)のフォールバック時のみ**という制約は変わらない。
  → ドロップダウンの選択肢は `prepare()` が返す `info.layouts`(マスタが持つレイアウト名一覧)をそのまま列挙する。
  → `mode: "clone"` が成立する通常ケースでは、このドロップダウンの選択値は使われない(無効化 or 「(自動: テンプレ追従)」と表示してグレーアウトする程度でよい)。
- 実装: `render.js` の `renderSpecs()`/`prepare()` に、ユーザー選択の `layoutId` を渡せる経路を追加し、
  `mode: "layout"` 時は `pickLayoutId()` の自動選択結果より優先する。

### T7. Hero風タグライン + その直下にPrompt入力(確定・新規)
- 画面最上部(ヘッダーのすぐ下)に、軽いHeroコピーを1行入れる。例:「考えを即、1〜2枚に。」のような、
  アプリの価値提案を一言で示すタグライン(具体的な文言は§3で確定させる)。
- そのすぐ下に `prompt` のtextareaを配置する。現状は「ラベル→textarea」だったところを
  「Heroタグライン→textarea」に置き換えるイメージ(ラベルは不要 or 控えめにする)。
- 目的: 「素材を貼るだけ」という体験を、ラベルの説明文でなくキャッチコピーで直感的に伝える。
