## 2. 申し送り: アルゴリズム・技術的に怪しい/注意すべき点

実装前にコードを読んで見つけた、**既存の脆さ**と**今回の変更で新たに踏み抜きやすい罠**。
「動いてるように見えて実は壊れている」を避けるため、着手前に必ず目を通すこと。

### 2-1. `geoKey` によるシェイプ突合せは座標の丸め一致に依存する(既存の脆さ、悪化させないこと)

`render.js` の clone モードは `geoKey(shape) = [type, round(left), round(top), round(width), round(height)].join("|")` という**位置・サイズの完全一致(丸め後)**でシェイプを突合せしている(`render.js:42`, `render.js:275`, `render.js:488`)。
`insertSlidesFromBase64(..., {formatting: "UseDestinationTheme"})` はテーマ差異によって微妙に座標がずれる可能性があり、ずれるとタイトル/リード/出典の`geoKey`が`plan.titleKey`等と一致せず、**「保持すべきシェイプ」が誤って削除される**(`else if (!info.plan.keepKeys[k]) sh.delete();` の分岐に落ちる)。
→ 今回のT6実装ではこの経路(`mode:"clone"`)には触れないが、**触れないことを確認する**(レイアウト選択は`mode:"layout"`限定、と明記したのはこのため)。もし将来この突合せロジックに手を入れるなら、丸め誤差の許容範囲(例: ±1pt)を持たせるなどの改善余地があることを認識しておく。

### 2-2. 解析(`prepare()`)の再入(re-entrancy)を現状のコードはガードしていない

現行`refreshReference()`は単純に`await SlideRender.prepare()`するだけで、二重発火(初回解析中にユーザーが再解析ボタンを押す、等)に対するガードが無い。
T3で「解析完了までgo disabled」を実装すると、**古い呼び出しが後から解決して`go`の状態を上書きする**競合が起きうる(例: 1回目の解析が重く、その最中に2回目を発火 → 2回目が先に終わって`go`をenabledにしたのに、1回目が後から終わって再度状態を書き換える)。
→ Phase 4で明記した通り、シーケンス番号か「直近に発火したPromiseの参照と一致するときだけ状態を反映する」ガードを必ず入れること。**これを入れないと、連打時に不整合なUI状態(ボタンが押せるのに古い`prepared`を使ってしまう等)が発生する。**

### 2-3. 選択スライドの変更を追跡していない(既存の未対応領域。今回のスコープでは見送るが認識しておく)

`prepare()`は呼び出された瞬間の`pres.getSelectedSlides()`を見るだけで、Office.jsの`onSelectionChanged`イベント等は使われていない。
つまり「Addin起動時に選択していたスライドA」を解析した後、ユーザーがPowerPoint側でスライドBを選択し直しても、**再解析ボタンを押さない限りタスクペインはスライドAの解析結果を保持し続ける**。
T3導入後は「構造解析が完了している=信頼できる最新状態」という前提でgoがenabledになるため、この**古い解析結果に基づいて誤ったスライドに対して生成してしまうリスク**が今まで以上に目立つようになる。
→ 今回のスコープには含めないが、実装者は最低限、ステータスアイコンのツールチップに「どのスライドを解析したか」が分かる情報(例: スライド番号)を出すことを検討してよい。将来的な改善候補として`docs/feature-proposals/`に別途起票することを推奨。

### 2-4. マスタが複数あるデッキでの `layoutId` の有効期限(T6の新規リスク)

`info.layoutId`(ユーザー選択値)を素朴にlocalStorageや変数に保持すると、**別のマスタに属するスライドを選んで再解析した後も古い`layoutId`が残ってしまう**可能性がある。Office.jsの`slides.add({slideMasterId, layoutId})`は、指定した`layoutId`が`slideMasterId`配下に存在しない場合にエラーになる(または無視される)可能性があり、動作が不定になりやすい。
→ Phase 7に明記した通り、**再解析のたびに現在のマスタの`info.layouts`に選択中の`layoutId`が含まれるか検証し、含まれなければ自動(先頭 or `pickLayoutId()`の結果)にリセットする**ガードを必ず入れること。

### 2-5. 進捗表示ヘルパーの共有先が3箇所ある(T4のリファクタ漏れリスク)

`stage()`/`startTimer()`/`stopTimer()`は`generate()`だけでなく`generateSections()`(`secGo`ボタン)と`redraw()`(将来は開発者モード限定の`redraw`ボタン)からも呼ばれている(`taskpane.js:219`, `taskpane.js:268`)。
「ボタン内ラップ表示」への置き換えを`go`ボタンだけ対応して満足すると、**章構成確認からの生成や再描画のときだけ古い(削除したはずの)進捗UIを探しにいって例外を吐く**、あるいは単に進捗が表示されなくなる、という不整合が起きる。汎用化した関数が3箇所すべてから同じ形で呼べることを確認すること。

### 2-6. プレビュー廃止時に `renderSpecs` へ `preview:false` を渡さない

T5の「プレビューをUIに出さない」を「PNGを取得しない」と読み替えて`renderSpecs(specs, {..., preview:false})`のように実装すると、**`DEBUG_SNAPSHOT`機能(開発者がスライド品質を目視確認するための仕組み)まで巻き込んで壊れる**(`render.js:529`の`opts.preview !== false && info.has18`の分岐でPNG自体が生成されなくなる)。UI側の表示コード(`showResult()`の`img`生成部分)だけを消し、`renderSpecs`呼び出しのオプションには一切触れないこと。

### 2-7. 強調色スウォッチの「自動」状態を見失わないこと

現行`palette()`は「`preset`が`"auto"`かどうか」という**1個のフラグ**で全てを判定している。スウォッチUIに作り替える際、UIの見た目(どのスウォッチがハイライトされているか)と、実際に`palette()`が返す値(`{}` or `{accent}`)が食い違う実装(例: スウォッチのハイライト管理とpalette()の判定ロジックが別々の変数を見ている)にしないこと。単一の状態変数(例: `selectedAccent: "auto" | "#RRGGBB"`)に一本化して両方がそれを参照する設計を推奨する。

### 2-8. Office WebView2上での `<input type="color">` の動作は実機確認が必須

`<input type="color">`はブラウザ標準でOSのカラーピッカーを開くが、Office task pane(WebView2ホスト)内でモーダルの位置・フォーカスの戻り先が想定通りになるかは環境依存の実績が薄い。実装後、実機のPowerPointデスクトップ版で実際にクリックしてピッカーが正しく開閉することを必ず目視確認すること(モックブラウザでの確認だけで「動いた」と判断しない)。

### 2-9. 開発者モードの入り口が未定義のまま実装が進むリスク

Phase 6で触れた通り、「スライド仕様JSON」欄を隠す条件(`?dev=1`かサーバフラグか)はこの計画書執筆時点でまだ実装方式が決まっていない。ここを決めずに「とりあえず`hidden`属性を付けて終わり」にすると、**開発者自身も含めて誰も再描画機能を使えなくなる**。実装者は方式を1つ選んで実装し、README.mdかこのファイルに使い方を追記すること。

## 3. 完了報告の基準

Phase 1〜7の実装が終わっても、**Phase 8(実機検証)を全項目消化するまで「完了」と言わないこと**。特に2-2・2-4・2-5は自動テストでは検知できない類の不具合(状態管理の競合・リファクタ漏れ)であり、実機での連打・切り替え操作でしか再現・確認できない。
