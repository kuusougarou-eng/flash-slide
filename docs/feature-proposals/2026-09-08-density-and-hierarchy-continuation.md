3. 箇条書きの折り返し2行目が点の位置に戻る→ Office.js `bulletFormat` にぶら下げインデント(marL/indent)を設定するAPIが無いことを実機で確認(indentLevel 0/1 とも無効)。折り返しを避ける方向(列幅に対して1行に収まる大きさを優先、ただし縮小は最大2pt)で対処。

   - 密度判定が `shrunk` フラグ頼みで、格子(table)セルの縮小を検知できなかった(フラグではなく実際の最小フォントサイズを見る必要があった)。
   - 章立て(`sections`)への切り替え後も、各章の生成が `maxSlides:1` 固定で密度保護の対象外という抜け道があった。
5. 「箇条書きの点をテキストボックスで分けるな」→ 調査の結果、コードは元々1シェイプで native bulletFormat を使っており分離していなかった(この具体的な訴えは、並行して動いていた別セッションが同時に見つけた `renderNestedItems`(パネル入れ子項目)の実際の分離バグとは別物。両者は無関係に存在し、両方直った)。

7. 「割り当てられる形(横長 vs 縦長)に応じて表現を変えるべきでは」→ `applyMethodology`(`cols`→`table` の自動組み替え、実際の列幅から折り返し行数を測って判定)という**既存の前例**を発見。同じ考え方をセル内の文章表現(散文 vs 箇条書き)に拡張。

## 確立された設計原則

1. **幾何に依存する表現選択はエンジン(測ってから決める)、意味構造はLLM(1回の推論で決める)。** OOXML直接操作を避ける判断(前の議論)と同じ理由: LLMは最終的な文字サイズ・列幅・折り返し位置を生成時点で知り得ない。
2. **静的な機械的分割より、LLMに複数表現を出させて描画側が選ぶ方が安全。** 「、」区切りでの自動箇条書き化のような静的分割は不自然さのリスクがある。
3. **文字サイズは重要度の階層。余白や密度の問題はサイズでなく整列・表現形式で解決する。**
4. **情報は文字数を理由に削らない。密度が高すぎるときはページを増やす(sections)。ただし入力自体が最初からページ構成を意識している場合(コンサル提案書の13枚構成など)は別の話** — これは次の一手で扱う。

### ① ラベル/値の構造分離(次点・低リスク)
並行スレッドの提案。`items` の要素を文字列だけでなく `{"label":"受注","value":"前年比 **+18%**"}` のようなオブジェクトでも許容し、描画側でラベル列を左に揃え、値だけを折り返す(ユーザーが提示した「灰色のラベル箱+白い内容箱」の再現)。
今回実装した `text`/`items` の二重表現の**自然な拡張**であり、セル単位(①で実装済み)より一段細かい「箇条書き1項目内」の階層化にあたる。コンフリクトしない。

### ② 文節単位の行送り(保留)
並行スレッドの提案。行頭に助詞1文字が残る(「で +1.5ptを狙う」のような)ケースを、幅が確定した後にエンジン側で調整する案。
**保留理由**: `estimateLines`/`charWidthEm` は文字幅の近似テーブルであり、実際の PowerPoint フォントメトリクスと一致しない(コード内コメントで自認済み)。生成時点でなく描画時点で判定するとしても、幅の見積り精度の問題自体は解決しない。着手するなら、行の折り返し全体を作り直すのではなく「行頭に単独の助詞だけが来るケースを検出して除外する」程度の狭い範囲に絞るべき。

### ③ 入力自体がページ構成を意識しているケースの扱い(未着手・要議論)
ユーザー指摘: 「コンサルの提案書は13枚構成で出すこともある(弊社理解と課題/ご提案骨子/骨子各論/プロジェクトアプローチ/WBS/成果物/役割分担/会議体/支援体制/お見積り/免責事項…)。1〜2枚に収めるのはあくまで既定で、入力(ユーザーのMarkdown等)が明らかに複数ページ構成を意図しているときはその限りでない」。
これは今回実装した「密度が高いから sections に逃がす」(事後的な密度検知)とは別の話で、**入力の時点で複数ページ構成の意図を検出し、密度チェックを待たずに最初から適切なページ数で生成する**プロンプト側の判断が要る。`server/prompt.js` の system prompt に、入力が構成済みのアウトライン(見出し・章立てを含むMarkdown、明確に独立した節の列挙)かどうかを判定し、その場合は sections を初手から使う指示を追加することになる。**未着手。次に着手する前に方針をユーザーと確認すること**(「1〜2枚を既定にする」という核心方針に例外を持ち込む変更のため)。

## 実施したこと

### ① ラベル/値の構造分離 — 実装・実機確認済み
- `items` の要素に `{"label":…,"value":…}` を許し、正規化(`panel()`)で「**ラベル**: 値」へ畳んで情報を落とさない。
  従来この形は `str()` が `[object Object]` を捨てていて**項目ごと消えていた**。
- `renderNestedItems` は、全項目がこの形で、かつラベル列を引いても説明が 1 行 12 字以上とれるときだけ 2 列に割る。
  ラベルは左に揃え、説明だけが折り返す。狭い列(3 パネル等)では従来どおり 1 つの文として流す。
- 実機で「売上総利益率」が 2 行に折り返した。原因は `charWidthEm` の近似のまま列幅を決めていたこと。
  `estimateLines` と同じ 0.95 の安全率を戻し、ラベルの箱は列幅いっぱいに取って間隔は箱の外に置いた(実機で 1 行に収まることを確認)。
- プロンプトにもこの形を明記した。

### ② `bulletFrom` は実機で効かなかった — 別シェイプに分ける方式へ変更
前セッションで入れた「見出し段落だけ点を外す」実装(`getSubstring().paragraphFormat.bulletFormat.visible`)は、
**実機では見出しにも点が付いていた**(PowerPoint の実描画で確認)。`paragraphFormat` は段落単位に効かず、
シェイプ全体に掛かる。ぶら下げインデントの API が無いのと同じ系統の制約。

疑似マーカーには戻さず、**見出し行と箇条書き行を別のテキストシェイプに分けて**セルの中で縦中央に置く方式にした。
箇条書き側は PowerPoint 本来の `bulletFormat` のまま。切り分け用の最小スペックを実機に描かせて確認済み。

(8 章で 6 枚しか描かれない)。章ごとの生成にも密度エスカレーションが掛かるため。

- `/api/generate` に `allowSections`(既定 true)を足し、章の生成では false を渡す。
  プロンプト(【枚数】)と server 側のエスカレーション判定の両方で sections を封じる。
- 万一 sections が返ってきたら 1 回だけ slides で問い直す。それでも 0 枚の章が残ればペインに章名を出す(黙って落とさない)。
- 修正後に同じ入力で再実行し、**8 章すべてがスライドを返した**(計 11 枚、sections 再エスカレーション 0 件)。
